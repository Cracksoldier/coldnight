Configuration

All user-facing settings live in themes/coldnight/_config.yml. Changes take effect after hexo generate or a dev-server restart.

Navbar

Controls the top navigation bar. Links accept any absolute path or external URL.

navbar:
  title: "My Blog"        # site name shown left of the navbar
  icon: "❄"               # brand icon before the title — image path or emoji/text; empty = built-in SVG logo
  icon_color: "#60a5fa"   # font colour for a text icon; ignored for images
  icon_after: ""          # optional second icon after the title (hides on mobile)
  icon_after_color: ""    # font colour for a text icon_after
  links:
    - name: Home
      url:  /
    - name: Archive
      url:  /archives
    - name: About
      url:  /about
KeyTypeDefaultDescription
navbar.icon string "" Brand icon rendered before the navbar title. Accepts an image path (/images/logo.png — detected by extension: svg png jpg/jpeg gif webp ico avif) or an emoji / short text snippet. Empty falls back to the theme's built-in SVG logo. Inline SVG in config is not supported — ship a file instead.
navbar.icon_color string "" Font colour for a text navbar.icon — hex, keyword, or modern colour functions incl. rgb(… / …), oklch(), var() (allowlist-validated; invalid values are silently dropped). Ignored for image icons; colour-emoji glyphs ignore CSS color.
navbar.icon_after string "" Optional image path or emoji/text rendered after the navbar title. Hides on mobile together with the title (the before-icon stays visible).
navbar.icon_after_color string "" Font colour for a text navbar.icon_after; same rules as navbar.icon_color.
favicon string "" Top-level key (not under navbar:). Favicon image path; the MIME type is derived from the extension. Empty or not an image path falls back to the theme's default favicon.svg + favicon.ico pair.

Cover images

KeyTypeDefaultDescription
cover.default string "" Absolute path to a fallback image used when a post has no cover_image in its front-matter.
cover.fallback boolean true Set to false to render posts without a cover_image with no card/hero thumbnail at all, instead of falling back to cover.default. The og:image meta tag keeps using cover.default either way, so social previews are unaffected.
cover.large boolean false Set to true to render card and hero thumbnails at full card width above the text instead of beside it (16/9). For cards this applies to list view only — grid cards already stack their cover on top. The pinned hero is affected at any grid.columns value, since it sits outside the post grid and is side-by-side by default there too. A post's cover_large front-matter overrides this in both directions, so a single post can go large on an otherwise compact index, or stay compact when the site-wide switch is on.
cover.aspect_ratio string "16/9" CSS aspect-ratio value applied to post-card thumbnails.

  default:      "/images/default-cover.jpg"
  fallback:     true
  aspect_ratio: "16/9"

Individual posts can opt out of the thumbnail with cover_image: false in their front-matter (bare YAML boolean, not "false") — the card and pinned hero render without a cover strip while og:image still falls back to cover.default.

Code blocks

KeyTypeDefaultDescription
code.copy_button boolean true Show a copy-to-clipboard button in the code block toolbar. Excludes line numbers from the copied text.
code.language_label boolean true Display the detected language name in the top-right corner of each code block.
code.collapse boolean true Auto-collapse long code blocks behind a “Show N more lines” button. Blocks only collapse when they exceed collapse_lines by at least 5 lines, so a block is never truncated for a trivial win.
code.collapse_lines number 25 Number of lines visible while a block is collapsed.

How it works

Code block enhancement is a two-part pipeline — a build-time filter and a client-side script — that work together to inject the toolbar without touching the Hexo renderer output.

Build time — scripts/helpers.js registers an after_render:html filter that runs on every generated HTML page after Hexo's renderer finishes. It scans for <figure class="highlight lang"> elements (the standard Hexo highlight output) and injects a data-lang="lang" attribute onto each one. This attribute is what makes the language label possible in CSS using attr(), and it also gives the JS a reliable hook to read the language name. At the same time the filter checks whether the first line of the code block is a filename comment (// filename:, # filename:, or /* filename: … */); if so it strips the comment from the displayed code and adds a data-filename attribute to the figure — see Code filename label.

Client side — source/js/copy-code.js runs on DOMContentLoaded and queries every figure.highlight. For each one it injects a .code-toolbar flex div into the top-right corner. The toolbar contains, left to right: an optional .code-filename-label (if data-filename is set), the language label (reads data-lang), and the copy button. The copy handler targets td.code specifically — not the entire figure — to exclude the gutter line-number column from the copied text.

The clipboard write uses navigator.clipboard.writeText() as the primary path. For non-HTTPS contexts (local preview over HTTP) where the Clipboard API is unavailable, it falls back to document.execCommand('copy') via a hidden <textarea>.

ℹ️

The site's _config.yml must use syntax_highlighter: highlight.js with hljs: true for Hexo to emit the expected <figure class="highlight lang"> structure.

LightGallery

LightGallery v2 JS and CSS are loaded via jsDelivr CDN only on post pages when enabled — no CDN requests on index, archive, tag, or category pages.

KeyTypeDefaultDescription
lightgallery.enabled boolean true Include LightGallery CDN assets. Disable for sites with no images or that need no external requests.
lightgallery.auto_mount boolean true Auto-wrap every .post-body img (not tagged .no-gallery) as a lightbox item on click. A single LightGallery instance is created on page load; clicking an image opens it at the correct index.
lightgallery.zoom boolean true Enable the LightGallery zoom plugin.
lightgallery.thumbnail boolean true Enable the thumbnail strip plugin at the bottom of the lightbox.

How it works

LightGallery CDN assets (JS and CSS) are gated by page.layout === 'post' in two places: the CSS <link> in _partial/head.ejs and the JS <script> tags in layout/post.ejs. This means zero CDN requests on any non-post page.

There are two mounting modes, both handled by source/js/gallery.js:

  • Auto-mount (auto_mount: true): On page load, gallery.js creates a single LightGallery instance targeting all .post-body img elements (excluding any with class .no-gallery). When the reader clicks an image, the handler calls instance.openGallery(idx) with the image's index — it reuses the existing instance rather than creating a new one on every click. This avoids the overhead of re-mounting LG per click and keeps memory usage flat regardless of how many images the post has.
  • Explicit {% gallery %} blocks: The tag plugin emits a <div class="lg-gallery" data-cols="N"> wrapper. gallery.js queries all .lg-gallery elements and mounts a separate lightGallery(el, { plugins: [...] }) instance on each one. Each block is fully independent.

The data-cols attribute (values 1–6) drives the CSS grid column count. A SCSS @for loop in _components.scss generates a rule for each value: .lg-gallery[data-cols="N"] { grid-template-columns: repeat(N, 1fr) }. Optionally enabled plugins (zoom, thumbnail) are only loaded when their respective config flags are true — the <script> tags for each plugin are conditionally rendered in post.ejs.

Post grid

Controls the layout of the index page. In grid mode, per_page is automatically set to columns × rows. In list mode (columns: 1), per_page is left untouched so the value in the site's _config.yml applies.

grid.rows number 3 Grid mode only. Rows per page; per_page is auto-set to columns × rows. e.g. columns: 2, rows: 4 → 8 posts per page. Ignored in list mode — set per_page in the site's _config.yml instead.

How it works

Column count needs to be known at two points: pagination (how many posts per page) and CSS layout (how wide each column is). The theme resolves both without requiring the user to set the same number in multiple places.

Pagination — scripts/helpers.js registers a before_generate filter that runs before Hexo builds any pages. It reads theme.grid.columns and theme.grid.rows and auto-sets config.index_generator.per_page = columns × rows. This ensures the index page always fills the grid exactly. In list mode (columns === 1) the filter leaves per_page untouched, so the site-level value applies.

CSS layout — Rather than hardcoding column counts in SCSS (which would require recompilation on every change), index.ejs injects the column count as inline CSS custom properties on the .post-grid element at render time:

<div class="post-grid"
     style="--post-grid-cols: 3; --post-grid-cols-md: 2;">

The SCSS rule in _layout.scss reads these via var(): grid-template-columns: repeat(var(--post-grid-cols), 1fr). Since CSS custom properties cascade, each .post-grid uses only its own values. The media-query breakpoints in SCSS switch to --post-grid-cols-md at tablet width and hard-code 1 column at mobile.

When grid.columns === 1, index.ejs also adds the post-grid--list modifier class, which overrides each .post-card to flex-direction: row with a fixed 180px thumbnail panel on the left.

Individual cards can opt out of that side panel: with cover_large: true in a post's front-matter (or cover.large: true site-wide, see Cover images), post-card.ejs adds a post-card--large modifier and the card returns to a stacked layout with a full-width 16/9 thumbnail above the text. Because the base card is already flex-direction: column, that rule only has to undo the list-view overrides — it is nested inside .post-grid--list, which is why it does nothing in grid mode.

The pinned hero has the same switch (pinned-post--large), swapping its 45%-wide side cover for a stacked one — but that rule is not nested under the grid modifier. The hero renders outside .post-grid and is flex-direction: row at every column count, so unlike the cards it restructures whenever the flag is set, grid mode included.

Links page

Controls the heading of the bookmark board at /links/. Both keys are empty by default, which reproduces the page exactly as it shipped before they existed: an h1 reading Links and no subtitle.

links:
  title:    "Bookmarks"                                  # empty = front-matter title, then "Links"
  subtitle: "Reference material worth keeping."       # empty = no subtitle line
KeyTypeDefaultDescription
links.title string "" Text of the page h1. When empty, falls back to the title: front-matter in source/links/index.md, then to the literal "Links".
links.subtitle string "" Optional standfirst rendered as .page-header__subtitle between the h1 and the link-count line. Empty = the element is not emitted at all.

Non-string values are ignored rather than stringified — a bare YAML title: false falls through to the next step of the chain instead of printing false as the heading. This is the same cfgStr guard used for the navbar brand slots.

Tag filtering

There is deliberately no config key for the tag filter — it is driven entirely by the data. Add a tags field to any entry in source/_data/links.yml and the chip bar appears; remove them all and it disappears.

- title:    "jq Manual"
  url:      "https://jqlang.github.io/jq/manual/"
  abstract: "Full reference for the command-line JSON processor."
  tags:     [cli, docs, reference]   # or a single bare value: tags: cli

The chips are single-select with a leading All chip, matching the archive filter chips. Each tagged card also renders its tags as clickable pills that activate the same filter. While a tag is active the count line reads 3 of 10 links; links with no tags are visible only under All. Filtering is client-side (links-filter.js, loaded only on this page) and uses the hidden attribute, so no URL changes and the unfiltered page is what search engines index.

Table of contents

Auto-generates a sticky TOC in the sidebar from post headings, and a floating bottom-sheet drawer on mobile. Add toc to sidebar.widgets to display the desktop widget. The mobile drawer is automatic — it appears on any post with headings when the sidebar is hidden (≤640px viewport). Both silently render nothing on headingless posts.

KeyTypeDefaultDescription
toc.enabled boolean true Enable the TOC widget, mobile drawer, and load toc.js + toc-drawer.js on post pages. Set to false to disable all three.
toc.max_depth number 3 Maximum heading level to include. 2 = ## headings only; 3 = ## and ###. H3 entries are indented in the list. Applies to both the sidebar widget and the mobile drawer. 
toc:
  enabled:   true
  max_depth: 3   # 2 = h2 only, 3 = h2 + h3

How it works

The TOC is built in two stages: a build-time helper generates the HTML list, and a client-side script handles scroll-spy active highlighting.

Build time — scripts/helpers.js registers a render_toc(content) Hexo helper. When the sidebar widget calls <%- render_toc(page.content) %>, the helper receives the already-rendered HTML of the post, scans it for <h2> and <h3> elements that have id attributes (Hexo's renderer assigns these automatically), and returns a flat <ol class="toc-list"> with one <li class="toc-item"><a class="toc-link" href="#id"> per heading. H3 entries get an additional toc-item--h3 class which adds left padding in CSS. If no qualifying headings are found, the helper returns an empty string and the widget renders nothing.

Client side — source/js/toc.js is loaded on post pages whenever theme.toc.enabled is true (the former sidebar-hidden guard has been removed). It uses IntersectionObserver with rootMargin: '0px 0px -65% 0px'. This rootMargin shrinks the observable area to the top 35% of the viewport — a heading is considered "active" the moment it enters that zone. When the observer fires, it reads the heading's id, finds the matching .toc-link by comparing href attributes, and toggles the active class (which applies an accent-colored left border). Because it queries .toc-link globally, scroll-spy highlighting works automatically for both the sidebar widget and the mobile drawer.

The toggle button in the widget sets or removes the hidden attribute on <nav id="toc-list"> and flips aria-expanded on the button. The CSS chevron rotation is handled entirely via the selector [aria-expanded="false"] svg { transform: rotate(180deg) } — no JS class toggling needed.

Mobile drawer — on viewports ≤640px the sidebar is CSS-hidden, so the TOC widget is not visible. _partial/toc-drawer.ejs is rendered in post.ejs inside the same toc.enabled gate. It calls render_toc(page.content) a second time at build time — if the result is empty it renders nothing; otherwise it emits a .toc-fab button (fixed bottom-right, visible only on mobile) and a .toc-drawer overlay + bottom-sheet panel with a slide-up animation. source/js/toc-drawer.js handles open/close: clicking the FAB opens the drawer, clicking the backdrop or close button closes it, pressing Escape closes it, and clicking any TOC link closes it (the browser then scrolls to the heading natively). Styles live in _components.scss under // ─── Mobile TOC floating button + drawer.

Search

Full-text search of post titles, content, and tags via a dropdown in the navbar. Requires hexo-generator-search and a search: block in the site _config.yml.

Add to the site-level _config.yml:

search:
  path:    search.json
  field:   post
  content: true
KeyTypeDefaultDescription
search.enabled boolean true Show the search input in the navbar. Set to false to hide it and skip loading search.js.

How it works

hexo-generator-search emits public/search.json at build time — a flat JSON array of post objects with title, content, url, and tags fields. source/js/search.js is loaded via _partial/footer.ejs on every page when search is enabled.

Subdirectory-safe URL — the <script> tag for search.js carries a data-search-url attribute set by footer.ejs via url_for('/search.json'). On startup, search.js reads this attribute from its own script element (document.querySelector('script[data-search-url]')) rather than hardcoding the path. This keeps the path correct for sites deployed in a subdirectory (e.g. https://user.github.io/repo/search.json).

Lazy fetch with shared promise — the JSON index is only fetched on the first focus event on either search input. The promise is stored in a module-level loadPromise variable. If the mobile drawer input is focused while the desktop-triggered fetch is in-flight, the second focus handler reuses loadPromise instead of starting a second request. After the fetch resolves, if the focused input already contains a query (the user typed before the network responded), runSearch() fires immediately so no keystrokes are lost.

Factory pattern — init(inputId, wrapperId, resultsId) is called twice at the bottom of the script: once for the desktop navbar input (search-input, search-wrap, search-results) and once for the mobile drawer input (search-input-mobile, search-wrap-mobile, search-results-mobile). Both instances share the same loadPromise and the same cached searchIndex array.

Matching — queries are debounced 180 ms. Each query is split on whitespace and all terms must match somewhere in the post's title, first 800 characters of content, or tags (AND logic). Results are capped at 8. esc() HTML-escapes all user-derived strings before insertion to prevent XSS. mark() wraps matched substrings in <mark> after escaping.

Keyboard navigation — Press / on any page to instantly focus the search input (no-op if an input, textarea, or contenteditable already has focus). ↓ / ↑ move focus between result <a> links. Escape closes the dropdown and blurs the input. Pressing ↑ while on the first result returns focus to the input. Clicking outside the search wrapper closes the dropdown. Press ? on any page to open a keyboard shortcuts modal listing all available shortcuts; it closes on Escape, click outside, or the × button. The modal is a native <dialog> element and is lazily created on first trigger.

Open Graph / SEO

All Open Graph, Twitter Card, and SEO meta tags are emitted from _partial/head.ejs automatically — no extra configuration is required. The following fields are populated from post front-matter and site config:

Meta tagSource
og:title / twitter:titlepage.title, falls back to config.title
og:description / twitter:description / meta descriptionpage.description → page.excerpt → start of the post body (all HTML-stripped + entity-decoded) → config.description. Capped at 160 characters.
og:image / twitter:imagecover_image front-matter → theme.cover.default; resolved to an absolute URL using config.url. The thumbnail opt-outs (cover.fallback: false, cover_image: false) do not affect this chain
og:typearticle on post pages, website everywhere else
og:site_nameconfig.title

article:published_time / article:authorpage.date / config.author — post pages only

How it works

All meta computation runs in a single <% %> block at the very top of _partial/head.ejs, before any HTML output. EJS templates are executed sequentially, so variables must be fully resolved before the HTML that references them is rendered.

Description fallback chain — descriptions come from the shared page_description helper (registered in scripts/helpers.js and also used by the llms.txt generator): front-matter description: → the excerpt (set by <!-- more --> or the excerpt: field) → the start of the post body. Each candidate is HTML-stripped, entity-decoded (&amp;, &lt;, &gt;, &quot;, &#39;, &nbsp;), whitespace-collapsed, and trimmed before the fallback decision, so an excerpt that is only an image or code block falls through to the body instead of producing an empty description. metaDesc is then built as (page_description(page) || config.description || '').slice(0, 160).

Conditional meta tags — og:image and twitter:image are only emitted when a cover image is actually resolved (to avoid serving an empty content="" attribute that some crawlers treat as an error). article:published_time, article:author, and the post-tag keyword list are only emitted on page.layout === 'post' pages. twitter:site is only emitted when theme.social.twitter is non-empty.

💡

Set url: in the site _config.yml to your production domain (e.g. https://example.com) so that og:image and canonical links are absolute URLs.

llms.txt

Opt-in support for the llms.txt convention — a Markdown index of the site at /llms.txt that LLMs and AI crawlers can consume without parsing HTML, plus an optional companion /llms-full.txt containing the complete Markdown body of every post and showroom project. Both files are generated at build time; nothing is loaded at runtime.

llms_txt:
  enabled: false   # opt-in — emit /llms.txt
  full:    true    # when enabled, also emit /llms-full.txt
KeyTypeDefaultDescription
llms_txt.enabled boolean false Emit /llms.txt: site title and description, then link lists for all posts (newest first), showroom projects, and remaining pages, each with a one-line description.
llms_txt.full boolean true Also emit /llms-full.txt — each post's and project's raw Markdown body with its URL, date, and tags. Set to false to publish only the index.

Per-page opt-out

Set llms_txt: false in any post's, project's, or page's front-matter to exclude it from both files — for unlisted pages you don't want advertised, or posts whose full text should not be packaged for LLM ingestion.

⚠️

Raw source is exported: /llms-full.txt contains each post's pre-render Markdown source. Render-time transformations — including content-protection plugins that encrypt the rendered HTML — do not apply to it. Opt affected posts out with llms_txt: false front-matter.

How it works

The generator is registered in scripts/helpers.js and returns plain-string routes, which Hexo serves as text/plain. It runs once per hexo generate; when disabled it returns immediately.

Index descriptions — each entry's one-liner comes from the same shared page_description chain used for og:description (front-matter description: → excerpt → start of the body, HTML-stripped and entity-decoded), capped at 200 characters on a word boundary. Projects use their subtitle: front-matter first. Link labels escape [ ] and link targets percent-encode parentheses and whitespace so titles and custom permalinks cannot break the Markdown link syntax.

Full file — /llms-full.txt uses each entry's raw Markdown source (page._content) rather than stripped HTML, so code blocks survive intact; <!-- more --> markers are removed. Theme tag plugins ({% note %}, {% tabs %}, …) appear unrendered.

JSON Feed

The theme emits /feed.json — a JSON Feed 1.1 — at build time, with a matching <link rel="alternate" type="application/feed+json"> in the page head. No plugin is required, and the feature is independent of social.rss: that key only controls the atom feed link, and the atom feed itself requires hexo-generator-feed.

json_feed:
  enabled: true    # emit /feed.json (JSON Feed 1.1)
  limit:   20      # number of newest posts included
KeyTypeDefaultDescription
json_feed.enabled boolean true Emit /feed.json and its <link rel="alternate">. Set to false to suppress both.
json_feed.limit number 20 Number of newest posts included in the feed. Invalid or missing values fall back to 20.

How it works

A generator in scripts/helpers.js serialises the newest posts to the JSON Feed 1.1 schema: id/url (canonical permalink), title, content_html, date_published, summary (same shared page_description chain as og:description), and tags. Root-relative href/src attributes in the content are rewritten to absolute URLs — feed readers resolve relative paths against their own origin, not yours.

date_modified is only set when the post has an explicit updated: in its front-matter — the same rule the "↻ Updated" badge and JSON-LD dateModified follow — so file-mtime noise on fresh clones never leaks into the feed.

Stats page

Opt-in: emits a /stats/ page with build-time posting statistics — total posts, total words, tag/category counts, posts-per-year bar chart, top-10 tag list, and the longest streak of consecutive months with at least one post. Zero client-side JavaScript: the bars are server-computed integer percentages.

stats:

How it works

A generator in scripts/helpers.js walks all posts once, counting words (code blocks excluded, same counter as word_count) and bucketing dates by year and month. Internal link checker

A build-time checker that warns about internal <a href> targets with no matching generated route — catching typos, renamed posts, and stale cross-references before they ship. External links are never touched (no network requests).

How it works

Two phases in scripts/helpers.js: an after_render:html filter collects every href as each page renders, and a before_exit filter validates them against the full route list once generation finishes. Related posts

When related_posts: true, a "You might also like" section renders up to 3 post cards at the bottom of every post page (below the post footer, above </main>). The scoring runs entirely at build time inside post.ejs — no plugin is required.

KeyTypeDefaultDescription
related_posts boolean true Show the "You might also like" section. Set to false to hide it on all posts.

Scoring algorithm

Every other post is scored against the current post, and the top 3 non-zero scores are shown:

  • +2 pts per tag that appears in both posts
  • +1 pt if both posts share the same primary category

Posts with a score of 0 are excluded. The section is hidden entirely when no candidates score above 0.

How it works

The entire scoring process runs at build time inside the top <% %> block of layout/post.ejs — there is no runtime JS and no external plugin. Because EJS is executed sequentially during hexo generate, all variables are fully resolved before the HTML template renders.

The code iterates site.posts using the Warehouse collection API's .each() method, which provides access to all posts and their metadata. To avoid O(n²) tag comparisons, the current post's tags are first loaded into a JavaScript Set via page.tags.each(t => _relatedTagSet.add(t.name)). The scoring loop can then check membership in O(1) with _relatedTagSet.has(t.name). All variables use the _related* prefix to avoid collisions with any EJS locals Hexo might inject.

The related posts section uses a fixed 2-column grid (--post-grid-cols: 2) rather than 3. The reason: the .post-page layout constrains the content column to approximately 700px. With 3 columns and 24px gaps, each card would be roughly (700 − 48) ÷ 3 ≈ 217px wide — too narrow for comfortable card layout. Two columns yields approximately 338px per card, matching the comfortable width seen at the tablet breakpoint on the home page. The section heading is an <h3> (not <h2>) to avoid conflicting with post body ## headings at the same document outline level.

Featured / Pinned post

Adding pinned: true to a post's front-matter promotes it to a full-width hero card above the index grid on page 1. No theme config toggle is needed — the feature is active whenever at least one post is pinned, and invisible otherwise.

BehaviourDetail
Which post becomes hero?The most recently dated post with pinned: true. If several posts are pinned, only the newest is shown as hero; the others appear in the grid normally.
Page 1Hero card renders above the grid. The pinned post is removed from the grid on this page to avoid duplication.
Page 2+Hero is hidden. The pinned post reappears in its chronological grid slot.
No pinned postIndex page renders exactly as before — no change.

The hero partial is _partial/pinned-post.ejs. It shows a 45%-wide cover panel on the left, a "Featured" badge, category, reading time, title, excerpt, date, and a "Read more" link. On mobile (<640px) the cover stacks above the content. Styles live in _components.scss under // ─── Pinned / Featured post.

How it works

Detection and deduplication both run at build time in layout/index.ejs. The top script block computes:

const pinnedPost = site.posts.sort('-date').toArray().find(p => p.pinned)
const showHero   = !!pinnedPost && (page.current === 1 || !page.current)

site.posts.sort('-date') sorts descending by date before calling .find(). This guarantees that when multiple posts have pinned: true, the most recently dated one becomes the hero — no explicit priority field is needed.

page.current is Hexo's pagination index (1, 2, 3, …). On single-page sites where per_page: 0 effectively disables pagination, Hexo sets page.current = undefined. The !page.current branch in showHero handles this case, ensuring the hero still appears on such sites.

Deduplication is handled inside the grid loop with <% if (showHero && post.path === pinnedPost.path) return %>. The && short-circuits: when showHero is false (i.e., no pinned post was found and pinnedPost is null), the right-hand side pinnedPost.path is never evaluated, so there is no null-reference error.

.pinned-post has min-height: 200px for two reasons: (1) it guarantees the hero has visual weight even for posts with only a title and no excerpt; (2) the cover panel is a flex child that stretches to the container's height — without a minimum height the container could collapse to roughly 80px on such posts, making the cover panel effectively invisible.

💡

Give the pinned post a cover_image for the best hero appearance — without a cover the hero displays content-only with a blue accent border.

KeyTypeDefaultDescription

How it works

How it works

Hexo's highlight.js renderer processes fenced code blocks before any theme filter runs. A mermaid block emits <figure class="highlight plaintext"> with a <code class="hljs mermaid"> inner element (mermaid is not a known highlight.js language, so it falls back to plaintext for the figure class but still applies the mermaid class to the code tag). The theme's after_render:html filter iterates every <figure> block; if the inner <code> has class mermaid, it decodes the HTML-escaped source and replaces the entire <figure> with <div class="mermaid">decoded source</div>.

Entity decoding — Hexo HTML-encodes the code content (&gt;, &amp;, line breaks as <br>, etc.). The filter decodes the most common entities before writing the source into the div. The <br> → \n conversion is the structurally essential one: highlight.js encodes newlines as <br>, but the Mermaid parser requires literal newline characters as statement separators.

Assets — Mermaid JS is vendored under themes/coldnight/source/vendor/mermaid/ (entry point mermaid.esm.min.mjs plus its chunked dependencies). It is injected as a <script type="module"> at the bottom of post.ejs only when mermaid.enabled is true — zero network requests on non-post pages and on sites with the feature disabled.

Theme safety — the theme value is validated against the pattern /^[a-z]+$/ before injection into the inline script to prevent code injection from a malformed config value. Unknown values fall back to dark.

KaTeX math

Renders $...$ (inline) and $$...$$ (display) LaTeX math delimiters as KaTeX HTML at build time. Zero runtime JavaScript — only the KaTeX CSS file is served to the browser.

KeyTypeDefaultDescription
math.enabled boolean true Enable build-time KaTeX rendering. When disabled, $...$ and $$...$$ are passed through as literal text and no KaTeX CSS is loaded. 
math:
  enabled: true   # render $...$ and $$...$$ as KaTeX math

How it works

Math rendering uses a two-filter pipeline so that the LaTeX source is never seen by the Markdown renderer:

  1. before_post_render — runs on the partially pre-processed Markdown. By the time this filter fires, hexo-renderer-marked has already wrapped fenced code blocks in <hexoPostRenderCodeBlock>…</hexoPostRenderCodeBlock> markers. The filter uses a single combined regex that matches those markers (and inline code spans) first and skips them unchanged, then replaces $$expr$$ with <div class="katex-d" data-e="…"> and $expr$ with <span class="katex-i" data-e="…"> placeholder tags. The expression is HTML-escaped into the data-e attribute so it survives the Markdown renderer intact.
  2. after_post_render (KaTeX) — finds the placeholder tags in the rendered HTML, HTML-unescapes the stored expression, and calls katex.renderToString(). A figure-skip guard in the same regex ensures any placeholders that somehow ended up inside a <figure> block (code block edge case) are left unchanged rather than rendered.

CSS — _partial/head.ejs conditionally emits a <link> to /vendor/katex/katex.min.css on post pages only when math.enabled is true. All KaTeX font files are self-hosted under themes/coldnight/source/vendor/katex/fonts/. No <script> tag is ever emitted — rendering is fully build-time.

Output — KaTeX uses its default htmlAndMathml output mode, which emits both the visual HTML and a <math> element for screen readers.

⚠️

The $...$ delimiter matches any two dollar signs on the same line, so prose containing currency amounts can trigger the renderer unintentionally. Escape a literal dollar sign with a backslash: \$50. See Writing — KaTeX math for the full false-positive guidance.

The theme includes a dedicated @media print stylesheet that produces a clean black-on-white printout from any post page. No configuration is required — the styles activate automatically when the browser's print dialog is opened or when generating a PDF via the browser.

  • Hides UI chrome — navbar, sidebar, back-to-top button, reading progress bar, TOC FAB, TOC drawer, permalink button, share buttons, related posts section, post navigation (prev/next), code toolbar, footer, toast container, skip-nav link, series nav, and the pinned post hero are all hidden.
  • Full-width content — the two-column grid collapses to a single column (.page-wrapper { display: block }) so the post body fills the page width.
  • External link URLs — external links in the post body have their URL appended in parentheses after the link text (e.g. Hexo (https://hexo.io)) so the destination is visible in print. The ↗ icon added by the external-link feature is suppressed so it doesn't appear before the URL.
  • Page breaks — h2 and h3 headings have page-break-after: avoid to prevent a heading from stranding alone at the bottom of a page. Code blocks, figures, and cover images have page-break-inside: avoid.

Print styles live in source/css/_print.scss and are imported at the end of style.scss so the @media print rules have correct cascade priority over the rest of the stylesheet.
