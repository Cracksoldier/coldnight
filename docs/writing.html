Writing

How to structure posts and use the theme's Markdown extensions.

Post front-matter

All fields except title and date are optional.

---
title:          My Post Title
date:           2026-01-15
updated:        2026-03-10            # optional; shows "↻ Updated YYYY-MM-DD" in post metadata when it differs from date
categories:    [Dev]
tags:           [javascript, hexo]
cover_image:    /images/cover.jpg     # optional; falls back to cover.default
cover_caption:  "Photo by Jane Doe"   # optional; wraps cover in <figure><figcaption>
excerpt:        "Override the auto-excerpt shown on post cards."
pinned:         true                  # optional; promotes post to featured hero on the index page
series:         "My Series Name"      # optional; groups post into a numbered series nav strip
---
FieldDescription
titleRequired. The post title shown in the header, page <title>, and og:title.
dateRequired. Publication date. Used for archive sorting and article:published_time.
categoriesArray of category names. The first is the primary category used in post cards and related-post scoring.
tagsArray of tag names. Used in the tag cloud widget, tag pages, related-post scoring, and OG keywords.
updatedExplicit last-modified date. When set and different from date, a "↻ Updated YYYY-MM-DD" badge appears in the post metadata row. If omitted Hexo falls back to the file's mtime — set this explicitly to avoid false badges on fresh git clones.
cover_imagePath to the post's cover image. Used on post cards, the post header, the pinned hero, and as og:image. Falls back to theme.cover.default if omitted.
cover_captionAttribution text shown below the cover image. When present the cover is wrapped in a <figure><figcaption> element and the img gets alt="" so screen readers don't announce both the caption and the alt text.
excerptOverride the auto-excerpt shown on post cards and in og:description. If omitted, Hexo uses the text up to the first <!-- more --> tag, or the start of the post body.
pinnedSet to true to promote this post to the featured hero card on index page 1. See Featured post.
seriesA string that groups this post with others sharing the same value. All matching posts appear in a numbered nav strip above the post body, sorted by date. See Series posts.
⚠️

mtime false positives: Hexo always populates page.updated — it defaults to the file's mtime when not set in front-matter. On a fresh git clone, all mtimes reflect the clone timestamp, which will differ from date: and trigger the "↻ Updated" badge on every post. Always set updated: explicitly in front-matter when you want to surface a revision date; omit it entirely when the post has never been revised.

💡

You can also use <!-- more --> anywhere in the post body to set the excerpt boundary instead of the front-matter excerpt field.

Footnotes

hexo-renderer-marked supports standard Markdown footnote syntax out of the box. The theme provides matching styles — no plugin or extra config required.

Syntax

Here is a sentence with a footnote.[^1]

A second reference uses the same syntax.[^note]

[^1]: This is the footnote text.
[^note]: Footnote labels can be any string — they render as sequential numbers.
ElementDescription
[^label]Inline reference. Renders as a superscript number linking to the footnote definition at the bottom of the post.
[^label]: textFootnote definition. Must appear somewhere in the post body (typically at the end). The label can be any alphanumeric string.
💡

Footnote labels are for authoring only — they always render as sequential integers (1, 2, 3, …) in the output regardless of the label string you use.

How it works

hexo-renderer-marked transforms [^label] references into <sup class="footnote-ref"><a href="#fn1" id="fnref1">[1]</a></sup> inline, and collects all definitions into a <section class="footnotes"> element at the end of the rendered HTML. The section contains an <hr> (hidden by the theme's CSS — the border-top on .footnotes replaces it) and a numbered <ol>. Each <li> ends with a <a class="footnote-backref">↩</a> that links back to the inline reference.

All styling lives in _typography.scss inside the .post-body, .prose { } block. The inline reference .footnote-ref a is styled as a small superscript in $accent-light. The .footnotes section gets a top border, smaller font size, and muted color to visually separate it from the main post body.

{% gallery %} tag

Renders a responsive photo grid powered by LightGallery. Each image opens in full-screen when clicked.

Syntax

{% gallery [cols] %}
![Caption text](/images/photo1.jpg)
![Another photo](/images/photo2.jpg)
![](/images/photo3.jpg)          # caption is optional
{% endgallery %}
ParameterTypeDefaultDescription
cols number 3 Number of columns in the photo grid. Supported values: 1–6. Each value maps to a dedicated CSS grid rule generated by a SCSS @for loop.

Example

{% gallery 2 %}
![Sunset over the mountains](/images/trip/sunset.jpg)
![Morning fog in the valley](/images/trip/fog.jpg)
{% endgallery %}

How it works

scripts/helpers.js registers gallery as a Hexo block tag plugin. When Hexo encounters {% gallery [cols] %}…{% endgallery %} during rendering, it calls the plugin with the block body as a string. The plugin scans the body for Markdown image syntax (![alt](src)), wraps each image in an anchor tag (<a href="src"><img src="src" alt="alt"></a>), and wraps the entire collection in:

<div class="lg-gallery" data-cols="N">
  <a href="/images/photo1.jpg"><img src="/images/photo1.jpg" alt="Caption text"></a>
  ...
</div>

The cols argument is clamped to 1–6 by the plugin; values outside that range default to 3. On post pages where LightGallery is enabled, source/js/gallery.js queries all .lg-gallery elements on page load and mounts a separate lightGallery(element, { plugins: [...] }) instance on each one. Each gallery block is fully independent — clicking an image in one gallery cannot open images from another.

The CSS grid column count is driven by the data-cols attribute. _components.scss generates rules for all six values via a SCSS @for loop:

@for $i from 1 through 6 {
  &[data-cols="#{$i}"] { grid-template-columns: repeat(#{$i}, 1fr); }
}

On mobile (≤640px) the SCSS overrides all data-cols values to 2 columns regardless of what was specified.

⚠️

lightgallery.enabled must be true in the theme config for gallery clicks to open the lightbox. The grid will still render without it, but clicking images won't open a full-screen viewer.

{% note %} tag

Renders a styled callout box. Markdown is supported inside the tag body.

Syntax

{% note type %}
Content here. **Markdown** is _supported_.
{% endnote %}
TypeColorIconWhen to use
tip Green ✓ Best practices, helpful hints
info Blue ℹ Neutral supplementary information
warning Yellow ⚠ Caveats, deprecated features
danger Red ✕ Breaking changes, data loss risks

Examples

{% note tip %}
Run `hexo clean` before `hexo generate` to avoid stale cache issues.
{% endnote %}

{% note warning %}
This option will be **removed** in a future release.
{% endnote %}

How it works

scripts/helpers.js registers note as a Hexo block tag plugin. The first word after note is the type; the plugin validates it against the four allowed values (tip, info, warning, danger) and renders an unknown type as info. The block body is passed to Hexo's built-in Markdown renderer so that bold, italic, inline code, and other Markdown syntax works inside the callout.

The output is a <div class="note note-{type}"> containing an inline SVG icon (hard-coded per type — no external icon font or image request) and the rendered body wrapped in a <p>:

<div class="note note-tip">
  <svg class="note-icon" ...></svg>
  <p>Run <code>hexo clean</code> before ...</p>
</div>

Each type has its own color scheme defined in _components.scss. note-tip uses green ($success / $success-bg), note-info uses blue ($accent / $info-bg), note-warning uses amber ($amber / $amber-bg), and note-danger uses red ($danger / $danger-bg). All color values are SCSS variables from _variables.scss — never hardcoded.

{% tabs %} tag

Renders a multi-tab content block. Switching between tabs is handled by pure CSS (no JavaScript) using hidden radio inputs. Markdown is fully supported inside each tab panel.

Syntax

{% tabs %}
<!-- tab Tab name -->
Content for the first tab. **Markdown** is _supported_.
<!-- endtab -->
<!-- tab Another tab -->
Content for the second tab.
<!-- endtab -->
{% endtabs %}

Example — code in multiple languages

{% tabs %}
<!-- tab JavaScript -->
```js
console.log('hello world')
```
<!-- endtab -->
<!-- tab Python -->
```py
print('hello world')
```
<!-- endtab -->
<!-- tab Rust -->
```rust
println!("hello world");
```
<!-- endtab -->
{% endtabs %}
ℹ️

Up to 10 tabs are supported per block. Tab names can contain spaces but must not contain -->.

How it works

scripts/helpers.js registers tabs as a Hexo block tag plugin. It parses <!-- tab Name --> … <!-- endtab --> markers to split the block into named panels. For each tab it emits a hidden <input type="radio"> with a unique ID, a matching <label> in the tab nav bar, and a <div class="tabs__panel"> for the content. Each panel body is passed through Hexo's synchronous Markdown renderer so fenced code blocks and other syntax work normally.

The "active tab" state is driven entirely by CSS: the checked radio input selects both the active label (via :checked ~ .tabs__nav .tabs__label:nth-child(N)) and the active panel (via :checked ~ .tabs__panels .tabs__panel:nth-child(N)). All non-active panels are display: none. Styles live in _components.scss under // ─── Tabs.

{% timeline %} tag

Renders a vertical timeline — ideal for changelogs, career histories, project journals, or any chronological list. Markdown is fully supported inside each entry body. All rendering is build-time; no JavaScript is required.

Syntax

{% timeline %}
<!-- entry 2026-01-15 :: My First Job -->
Description text. **Markdown** is _supported_.
<!-- endentry -->
<!-- entry 2025-06-01 :: Open Source Project -->
Another entry body. You can include lists, code, and more.
<!-- endentry -->
{% endtimeline %}

Each entry is delimited by <!-- entry DATE :: TITLE --> and <!-- endentry -->. The :: separator splits the date from the title. Order is author-controlled — entries are rendered in the order they appear, with no automatic sorting.

FieldRequiredDescription
DATENoAny string used as the date label (ISO format recommended, e.g. 2026-01-15). Omit it entirely by writing <!-- entry :: Title only -->.
TITLENoThe entry heading. Omit it by writing <!-- entry 2026-01-15 --> with no ::. Both date and title can be omitted if the body is self-describing.
bodyNoAny Markdown content between the open and close markers. Rendered via Hexo's synchronous Markdown renderer, so fenced code blocks, bold, lists, etc. all work normally.

Example — changelog

{% timeline %}
<!-- entry 2026-03-01 :: v1.3.0 -->
- Added `{% timeline %}` tag plugin
- Added mobile TOC drawer for long posts
- Updated KaTeX to 0.16
<!-- endentry -->
<!-- entry 2026-01-10 :: v1.2.0 -->
- KaTeX math rendering (`$...$` and `$$...$$`)
- Mermaid diagram support
<!-- endentry -->
<!-- entry 2025-11-20 :: v1.0.0 -->
Initial public release.
<!-- endentry -->
{% endtimeline %}

How it works

scripts/helpers.js registers timeline as a Hexo block tag plugin. It scans the block content for <!-- entry DATE :: TITLE --> markers using a single regex pass, then for each match it:

  1. Splits the header on the first :: to extract the date (left side) and title (right side). If :: is absent, the whole header is treated as the date and title is empty.
  2. Passes the body text through Hexo's synchronous Markdown renderer (renderSync), identical to the pattern used by {% note %} and {% tabs %}. Falls back to a <pre>-escaped literal if the renderer throws.
  3. Emits a .timeline__entry containing a dot marker, a date <time>, a title <span>, and the rendered body.

If no valid entries are found the tag emits nothing — safe to leave partially filled. The vertical connecting line is a CSS ::before pseudo-element on .timeline positioned to run through the centre of the entry markers. Styles live in _components.scss under // ─── Timeline.

💡

The :: separator can appear in the title itself if needed — only the first occurrence splits the date from the title. For example, <!-- entry 2026-01-01 :: Title :: with colons --> sets the date to 2026-01-01 and the title to Title :: with colons.

{% spoiler %} tag

Wraps content in a native HTML <details>/<summary> block — a collapsible section the reader can open and close. Useful for answers, hints, tangents, or long code examples that shouldn't dominate the reading flow.

Syntax

{% spoiler label text %}
Content goes here. **Markdown** is supported.
{% endspoiler %}
ArgumentRequiredDescription
label textNoText shown on the collapsed summary row. Defaults to Show spoiler when omitted. Multi-word labels are supported — all arguments are joined with spaces.

Examples

Default label:

{% spoiler %}
The answer is 42.
{% endspoiler %}

Custom label with Markdown body:

{% spoiler Show solution %}
1. Start by initializing the repository.
2. Run `npm install`.
3. Copy `.env.example` to `.env` and fill in the values.
{% endspoiler %}

Spoilers can nest callouts, code blocks, or any other Markdown content:

{% spoiler Reveal the algorithm %}
```js
function binarySearch(arr, target) {
  let lo = 0, hi = arr.length - 1
  while (lo <= hi) {
    const mid = (lo + hi) >>> 1
    if (arr[mid] === target) return mid
    arr[mid] < target ? lo = mid + 1 : hi = mid - 1
  }
  return -1
}
```
{% endspoiler %}

How it works

scripts/helpers.js registers spoiler as a Hexo block tag plugin. It joins all arguments with spaces to form the label (HTML-escaped via escHtml), then passes the block body through Hexo's synchronous Markdown renderer (renderSync) with a try/catch fallback — identical to the pattern used by {% note %} and {% tabs %}. The output is a <details class="spoiler"> element containing a <summary> and a <div class="spoiler__body">.

The toggle triangle is a CSS ::before pseudo-element on .spoiler__summary that rotates 90° when the [open] attribute is present on the parent <details>. The default browser disclosure marker is hidden via list-style: none (Firefox) and ::-webkit-details-marker { display: none } (Chrome/Safari). Styles live in _components.scss under // ─── Spoiler.

💡

The <details> element is keyboard-accessible natively — Enter and Space open and close it without any JavaScript.

{% download %} tag

Renders a prominent download button. An optional external keyword adds an amber badge to indicate the file is hosted on a third-party server.

Syntax

{% download url [label] [external] %}
ArgumentRequiredDescription
urlYesAbsolute or root-relative URL to the file
labelNoButton text. Defaults to the filename parsed from the URL.
externalNoLiteral keyword. Adds an amber "External" badge next to the button.

Examples

{# URL only — label inferred from filename #}
{% download /downloads/app-v1.0.zip %}

{# Explicit label #}
{% download /downloads/app-v1.0.zip My App v1.0 %}

{# External file with label #}
{% download https://github.com/user/repo/releases/download/v1.0/app.zip My App v1.0 external %}

{# External file, label inferred #}
{% download https://cdn.example.com/report.pdf external %}

How it works

scripts/helpers.js registers download as an inline Hexo tag (no body, no {% enddownload %}). It emits a .download-block wrapper containing a .btn.btn--primary anchor with the download and rel="noopener noreferrer" attributes. When external is present, an amber .download-block__ext-badge span is appended beside the button. The label and URL are HTML-escaped via the shared escHtml utility before output.

ℹ️

The HTML download attribute only works for same-origin URLs. For files hosted on external servers the browser may open the file inline rather than downloading it. Most CDNs and file hosts set Content-Disposition: attachment headers, which force a download regardless — use the external flag to signal this to readers.

Styles live in _components.scss under // ─── Download block. The button reuses the existing .btn + .btn--primary classes — no extra button CSS is needed.

{% video %} tag

Embeds a responsive 16:9 video — YouTube, Vimeo, or a direct video file — with an optional caption. No JavaScript configuration required; the tag handles all URL patterns automatically.

Syntax

{% video url [caption words] %}
ArgumentRequiredDescription
urlYesYouTube URL (youtube.com/watch?v=… or youtu.be/…), Vimeo URL (vimeo.com/…), or direct video file path (.mp4, .webm, .ogv). Unrecognised URLs render as a plain link — no error.
captionNoAll words after the URL are joined and used as the caption text (shown below the embed in a <figcaption>). Also used as the iframe title attribute for accessibility.

Examples

{# YouTube — full URL #}
{% video https://www.youtube.com/watch?v=dQw4w9WgXcQ %}

{# YouTube — short URL with caption #}
{% video https://youtu.be/dQw4w9WgXcQ Never Gonna Give You Up %}

{# Vimeo #}
{% video https://vimeo.com/123456789 Conference keynote %}

{# Self-hosted MP4 with caption #}
{% video /videos/demo.mp4 Product walkthrough %}

How it works

scripts/helpers.js registers video as an inline Hexo tag (no body, no {% endvideo %}). The first argument is the URL; all remaining arguments are joined with spaces to form the optional caption. URL matching runs in priority order: YouTube patterns are checked first (both youtube.com/watch?v= and youtu.be/ short links), then Vimeo, then direct video file extensions. The matched id or path is HTML-escaped via escHtml before being written into the embed HTML.

YouTube and Vimeo embeds use <iframe> with loading="lazy". Direct files use a native <video controls preload="metadata"> element. All three are wrapped in a .video-embed__wrapper div that uses aspect-ratio: 16 / 9 and absolute-positioned children so the embed fills the wrapper at any width.

The output structure:

<figure class="video-embed">
  <div class="video-embed__wrapper">
    <iframe src="https://www.youtube.com/embed/ID" ... loading="lazy"></iframe>
  </div>
  <figcaption>Optional caption</figcaption>
</figure>

Styles live in _components.scss under // ─── Video embed. The figcaption style is inherited from the existing .post-body figcaption rule in _typography.scss — no extra caption CSS is needed.

Code block filename label

Place a filename comment as the very first line of any fenced code block. The theme strips the comment from the displayed code and shows it as a filename chip in the code toolbar, to the left of the language label.

Syntax

Use the comment style that matches the language:

// filename: src/utils/format.js   {# JavaScript, TypeScript, Go, Java, C/C++, Rust, CSS-in-JS #}
# filename: scripts/build.py      {# Python, Ruby, Shell, YAML #}
/* filename: src/styles/reset.css */ {# CSS, SCSS, Less #}

Examples

```js
// filename: src/app.js
export function greet(name) {
  return `Hello, ${name}!`
}
```

```python
# filename: scripts/deploy.py
import subprocess
subprocess.run(['hexo', 'generate'])
```

```css
/* filename: src/styles/base.css */
*, *::before, *::after { box-sizing: border-box; }
```

The toolbar for the first example renders as [ src/app.js   js   📋 ] — filename first, then language, then copy button. Code blocks without a filename comment are unaffected.

How it works

The after_render:html filter (Pass 1) in scripts/helpers.js processes the full <figure class="highlight"> HTML using a regex. It looks for an <span class="hljs-comment"> element matching any of the three comment patterns (//, #, /* ... */) immediately followed by a <br> as the first content in the code block. When found, the comment span is stripped from the body and a data-filename attribute is added to the <figure> element (value is HTML-escaped).

Client-side, copy-code.js reads data-filename in addCopyButton() and prepends a <span class="code-filename-label"> to the toolbar before the language label. The filename chip uses $text-primary colour with a right border to visually separate it from the muted language label. Styles live in _code.scss. Long filenames are capped at max-width: 220px with text-overflow: ellipsis.

💡

The filename comment is stripped from the displayed code but is not stripped from what the copy button puts on the clipboard — the raw code cell text is copied verbatim. If you want the filename excluded from copies too, omit the comment entirely and just annotate it in prose above the block.

Mermaid diagrams

When mermaid.enabled: true, fenced ```mermaid blocks are converted to rendered SVG diagrams. Requires no extra front-matter — any post can include diagrams.

Syntax

Use a standard fenced code block with the language identifier mermaid:

```mermaid
flowchart LR
    A[Write Post] --> B{Has diagrams?}
    B -- Yes --> C[Add mermaid block]
    B -- No  --> D[Publish]
```

Supported diagram types

Any diagram type supported by Mermaid v10 works: flowchart, sequenceDiagram, classDiagram, stateDiagram, erDiagram, gantt, pie, mindmap, and more. See the Mermaid documentation for full syntax reference.

Examples

```mermaid
sequenceDiagram
    Browser->>Server: GET /posts/my-post
    Server-->>Browser: 200 OK (HTML)
    Browser->>Browser: Render KaTeX
```

```mermaid
pie title Build time split
    "Markdown" : 42
    "SCSS"     : 25
    "Helpers"  : 33
```
ℹ️

Mermaid diagrams are rendered client-side from the diagram source that was baked into the HTML at build time. The Mermaid JS library and all its assets are self-hosted — no CDN requests. Configure the theme via Mermaid configuration.

KaTeX math

When math.enabled: true, $...$ (inline) and $$...$$ (display) LaTeX delimiters are rendered to KaTeX HTML at build time. No JavaScript runs on the page — equations are static HTML from the moment the page loads.

Inline math

Wrap a LaTeX expression in single dollar signs to render it inline with the surrounding text:

Einstein's equation, $E = mc^2$, is well known.
The quadratic formula gives $x = \frac{-b \pm \sqrt{b^2 - 4ac}}{2a}$.

Display math

Wrap a standalone expression in double dollar signs to render it centred on its own line:

$$\int_{-\infty}^{\infty} e^{-x^2}\, dx = \sqrt{\pi}$$

$$\begin{aligned}
x &= r\cos\theta \\
y &= r\sin\theta
\end{aligned}$$
💡

Math inside fenced code blocks or inline code spans (`$x$`) is never processed — it remains as literal text.

Avoiding false positives

The $...$ delimiter matches any two dollar signs on the same line, so prose containing currency amounts can trigger the renderer unintentionally. For example:

The item costs $50 and saves $30.   ← "50 and saves" renders as math!

To avoid this, escape literal dollar signs with a backslash:

The item costs \$50 and saves \$30.  ← rendered as plain text

Display blocks ($$...$$) are less prone to false positives because they require a blank line around them. See KaTeX configuration for implementation details.

Image captions

When image_captions: true in the theme config (enabled by default), images written as standalone paragraphs are automatically upgraded to <figure> + <figcaption> elements at build time. The caption text is taken from the Markdown alt attribute.

Syntax

![This text becomes the caption](/images/photo.jpg)

Renders as:

<figure>
  <img src="/images/photo.jpg" alt="This text becomes the caption">
  <figcaption>This text becomes the caption</figcaption>
</figure>
💡

Images with an empty alt attribute (![](/images/photo.jpg)) are left as plain <img> elements — no caption is added. This is useful for decorative images that shouldn't have a caption.

The conversion is applied by the after_render:html filter in scripts/helpers.js — it runs on every page after HTML rendering. Set image_captions: false in the theme config to disable it.
